# Recon

**Exact matching settles 72%. Fuzzy matching settles another 14%. The LLM,
bounded by a deterministic validator, settles the last 2% — and every wrong
match is reported.**

A reconciliation engine that matches bank settlement lines to the orders they
cover. Built to answer one question honestly: where does deterministic code
end and a language model begin?

---

## The problem

When a payment processor settles to a merchant, it sends one batched deposit
covering many orders — minus fees, minus refunds, minus chargebacks. The
merchant's bank statement shows the deposit. Their internal records show the
orders. These rarely match cleanly:

- A reference arrives truncated: `ORD-2026-0042` becomes `ORD-2026-42`.
- Three orders settle as one deposit.
- A refund makes the deposit ₹300 short.
- A fee makes it ₹12 short.
- A line appears twice.

Reconciling the statement back to the orders is manual, slow, and
error-prone. The wrong way to automate it is to point a model at it and hope.
The right way is to use deterministic code wherever the answer is knowable,
a model only where it isn't, and a validator to catch the model when it's
wrong.

## The claim

> Exact matching settles 72%. Fuzzy matching settles another 14%. The LLM,
> bounded by a deterministic validator, settles the last 2% — and every wrong
> match is reported.

That is the whole design. The model never decides a match. It **proposes**
one, with a reason and arithmetic. A pure, deterministic function then
**disposes**: it re-derives the arithmetic, checks the proposed order against
the candidate set the model was given, and rejects anything that doesn't add
up. Rejected proposals stay unresolved. A confident wrong answer is worse
than an honest "I don't know."

matched_ledger.csv + eval/report.md

The LLM sits behind the validator. The validator is a pure function of
`(proposal, candidate_orders, settlement_amount)` — no I/O, no clock, no
randomness. If it rejects, the row stays unresolved.

## Results

Full report: `eval/report.md`. Regenerated by the harness, never hand-written.

### Held-out split (153 rows, threshold 0.85)

| | Stage 1 | + Stage 2 | + Stage 3 |
|---|---|---|---|
| precision | 1.0000 | 0.9921 | **0.9924** |
| recall | 0.6471 | 0.8235 | **0.8562** |
| wrong matches | 0 | 1 | **1** |
| unresolved | 52 | 24 | **19** |

The held-out split was committed before any matcher was written. Its hash is
in `heldout.json`; `python -m src.split --verify` recomputes and checks it.
No parameter was tuned on it.

Two rows carry the honest story. `partial_refund` resolves **zero** — the
validator refuses to infer a refund when none is recorded, which is the
behavior D-09 chose. `fee_difference` carries **both** wrong matches; the fee
path is the least reliable, and the report says so.

### The validator is not a rubber stamp

Of the 71 rows Stage 2 could not resolve, the LLM proposed a match for 23 and
declined 48. The validator accepted 12 and rejected 11.

**Rejection rate on proposals: 48%.** The model tried to match nearly half
the time, and the deterministic check said no to almost half of those
attempts. That is the architecture claim, measured.
## How to read these numbers

**Dev precision (0.9937) is marginally higher than held-out (0.9924).** That
is the correct direction: the split was committed before tuning, so held-out
being slightly worse is expected, not a sign of overfitting.

Three things a reviewer should weigh, stated here rather than buried.

**The data is synthetic, and I generated it.** `orders.csv` and
`settlements.csv` are produced by `src/generate.py` from a seed. Because I
wrote the corruption model, I know the correct answer for every row — that is
what makes the metrics possible. It is also the main limitation: a real bank
feed has corruption shapes this model does not cover.

**The 0.99 precision is on data I control.** The `wrong_match_rate` is 1 in
132 — a single merged-sum coincidence where two unrelated orders summed to a
settlement amount. At this sample size, one error is within noise. The honest
framing is that precision is high on *this* corruption model, not that it is
high in general.

**The LLM's contribution is small — 12 rows.** The deterministic layers
resolve 438 of 509. The model adds 2%. That is the point: it is used only
where deterministic code cannot decide, and the validator ensures it adds no
errors. A larger LLM contribution would mean the deterministic layer was
under-built.

**The threshold is a recall knob with no precision cost on dev.** On dev,
precision is 1.0 at every threshold from 0.60 to 0.99. The threshold trades
only recall. See D-08.

## Limitations

By design:

- **Synthetic data only.** No live bank feed, no real PII.
- **The merged-sum path is brute-force.** O(n²) for pairs, O(n³) for triples.
  Fine at this scale; a real system would index by amount.
- **The LLM sees at most 5 candidates per row.** A row whose correct order is
  outside the top 5 by similarity is unresolvable by Stage 3.

Known gaps:

- **The one wrong match is a merged-sum coincidence.** Two unrelated orders
  summed to a settlement amount. Requiring the settlement reference to name
  its orders would fix it; left as future work.
- **The corruption model is one of several possible.** Truncation,
  substitution, merging, refunds, fees, duplicates, noise. Other real-world
  shapes are not modelled.
- **Stage 2's merged detection cannot tell a real merge from a coincidence**
  when the reference carries no order IDs.
